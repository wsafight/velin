# Velin 路线图

[English](ROADMAP.md)

Velin 的目标不是追齐 Rhai 或其他通用脚本语言。它要成为一套生产级的确定性脚本运行时：脚本描述规则、状态和控制流，宿主保留 I/O、权限与领域行为，执行可以受限、暂停、恢复和回放。

本路线图描述方向与验收条件，不承诺发布日期。已经发布的行为以[语言参考](LANGUAGE.zh-CN.md)、[架构](ARCHITECTURE.zh-CN.md)和仓库中的 `CHANGELOG.md` 为准。

## 当前基础

`0.4.x` 已经具备继续演进所需的核心边界：

- 确定性的五类值、显式种子随机数和可克隆机器状态。
- 源码到寄存器字节码的完整管线，以及反序列化时重新执行的字节码校验。
- `Yield::Host` / `resume` 宿主协议、无返回值效果批处理和有界宿主队列。
- 保守类型推断、宿主 schema 检查和确定赋值分析。
- 可复用的普通运行器与纯模块调用器、二进制 artifact、运行时执行镜像和执行 profile。
- Rust、C 和 WebAssembly 运行入口，以及 CLI、LSP、VS Code 扩展和 Playground。

这些能力是后续工作的约束，不是为了扩展语言而临时保留的实现细节。

## 演进原则

每项新能力都必须满足以下原则：

1. **外部效果仍然显式。** 新能力不能绕过 `perform` 直接访问文件、网络、时钟、界面或系统随机源。
2. **可复现状态仍然完整。** 快照必须包含影响后续执行的全部 VM 状态；相同程序、输入和种子必须重放相同结果。
3. **不信任输入仍然有界。** 新的语法、调用栈、模块、值形状和工具协议必须在分配大对象前施加预算。
4. **工具链与运行时共享语义。** 解析器、检查器、编译器、VM、LSP、Wasm 和 C API 不得各自发明兼容但不同的规则。
5. **稳定边界小于内部实现。** 源语言、门面 API、artifact 和 ABI 分别声明兼容范围；内部 AST、IR 和优化计划不成为永久格式。

开发顺序为 **P0 → P1 → P2 → P3**；性能与体积证据从 P0 开始，贯穿所有优先级。

## P0：执行边界与兼容契约

先稳定运行时边界，再增加语言表面积。P0 是后续所有能力的前置条件。

### 可配置执行预算

引入统一的执行策略，由 `Machine`、`ScriptRunner`、invoker 和纯模块共享。策略至少覆盖：

- 跨多次 `run` / `resume` 累计的总 fuel。
- 单次立即执行 fuel、宿主效果数量和调用深度。
- 单值、整机状态、宿主载荷和宿主队列的数据预算。
- 可由宿主触发的协作式取消或进度回调。

取消和墙钟超时属于宿主策略，不进入脚本可观察的值语义。快照是否保存累计 fuel 必须有唯一、经过测试的规则。预算耗尽、取消、非法字节码和宿主契约错误应具有可区分的错误类型。

完成条件：所有高级执行入口都接受同一种策略；在宿主效果之间反复恢复不能重置累计预算；默认策略仍适合直接运行不可信脚本。

### 分层兼容政策

分别定义并测试四类契约：

- **源语言**：哪些语法和运行时行为在当前发布线内保持兼容，以及发生变化时如何提供迁移说明。
- **Rust API**：门面 crate 遵循 SemVer；低层实验 API 明确标记稳定性。
- **Artifact**：格式携带版本，提供有限兼容窗口或显式离线迁移工具。
- **C ABI**：不透明 handle、ABI 版本查询、结构体布局规则和 append-only 扩展政策。

通过 golden fixtures 持续运行旧源码、旧 artifact 和旧宿主集成。安全支持范围必须与当前发布线同步。

完成条件：每个公开边界都有书面兼容政策、CI fixture 和废弃流程；不兼容变化都附带迁移说明并记录在变更日志中。

## P1：强类型宿主 SDK

P0 的边界稳定后，在不把原生对象放入 VM 的前提下，让宿主命令的接入成本接近普通 Rust 函数调用。

### 单一 schema 来源

从一份声明生成或构建：

- 静态检查使用的 `HostSchema`。
- 运行时使用的 ID 分派、参数检查和返回值检查。
- 同步和异步宿主驱动器。
- LSP 补全、签名帮助和 hover 元数据。
- 可选的 Rust 宏、C header 描述和 TypeScript 类型。

错误的参数、绑定形式或返回类型应在能静态证明时由检查器报告，其余情况在效果执行前或恢复时报告。

### 值编组

提供受预算约束的 Serde 与 `Value` 转换，并补齐 C 与 WebAssembly 的 List/Record 输入输出。转换必须保留整数范围、稳定记录顺序和明确的错误路径。

任意 Rust 类型、借用引用和原生方法不会成为新的 `Value` 变体。宿主持有的领域对象使用显式 ID 或可序列化 DTO 表示，权限校验仍由宿主完成。

完成条件：一个宿主命令声明可以同时驱动检查、运行时分派和编辑器提示；普通宿主不再手写名称匹配与重复的类型检查。

## P2：可组合的 DSL

这一阶段解决脚本复用和组织问题，但不转向通用动态语言。它依赖 P0 的资源边界，并复用 P1 的宿主 schema。

**状态：当前工作树中已完成。** 模块在编译期解析，纯函数调用在无环调用图上以卫生方式展开，小型语法均 lowering 为现有受检查操作。

### 模块和纯函数

已交付能力：

- 由宿主控制 resolver 的编译期模块导入。
- 显式导出和循环依赖诊断。
- 带参数、局部变量和返回值的命名纯函数。
- 初始版本使用无递归调用图；只有在调用栈预算、诊断和快照语义成熟后才重新评估受限递归。

纯函数不能执行 `perform`，也不能读取时钟、系统随机源或其他隐藏状态。状态机控制流和宿主效果继续留在顶层脚本；纯模块仍是值输入/值输出的隔离执行单元。

### 小型语法改进

在不增加新值语义的前提下，以下高收益语法已经可用：

- `for`、`break` 和 `continue`。
- List/Record 字面量。
- 集合读取索引和简单赋值缩写。
- `+=` 等可明确 lowering 为现有操作的赋值语法糖。

每项语法必须同时进入 parser recovery、静态检查、字节码校验、调试位置、资源预算、Wasm 和 C artifact 测试。

完成条件：脚本能够组织成多文件模块并复用纯计算，不依赖复制粘贴、标签模拟函数或动态代码执行。

## P3：完整的领域工具链

最后建设工具链，利用小型语言和宿主 schema 的可分析性，提供比通用动态语言更准确的体验。跨模块能力依赖 P2 的模块语义。

计划能力包括：

- 官方 formatter 和确定性的格式检查模式。
- semantic tokens、rename、signature help、code actions 和 workspace symbols。
- 跨模块 definition/reference，以及模块依赖诊断。
- 基于宿主 schema 的命令说明、参数提示和错误定位。
- 基于 `DebugTable` 的断点、单步、变量查看、效果边界暂停和 profile 源码映射。
- Playground 中的暂停、恢复、快照和确定性分支回放。

完成条件：常规脚本编辑、重构和调试不需要阅读字节码或手工对应 PC；LSP 与调试器只消费核心提供的解析、检查和 debug metadata。

## 跨阶段工作：性能与体积证据

性能工作从 P0 开始并贯穿全部阶段，而不是最后一次优化冲刺。基准分为三组：

1. **共享语言能力**：整数、布尔、字符串、列表、记录、条件和循环。
2. **嵌入成本**：冷编译、artifact 加载、热执行、宿主往返、效果批处理和机器重启。
3. **Velin 特有路径**：快照、回放、执行镜像、C ABI、Wasm 和队列背压。

结果记录延迟、吞吐、分配、峰值内存和原生/Wasm 体积。与 Rhai 等引擎的比较只覆盖双方语义一致的子集，并固定版本、feature、硬件、工具链和计时边界。CI 使用 Velin 自身的历史基线设置回归门禁；跨引擎数字用于理解取舍，不作为普遍更快的宣传结论。

完成条件：公开结果可以从仓库命令复现，发布说明能够解释显著回归或改进，优化不能绕过语义测试与资源统计。

## 明确非目标

以下能力不在本路线图内：

- 与 Rhai、JavaScript、Lua 或其他通用语言实现语法/API 兼容。
- 闭包、函数指针、运行时 `eval`、动态 import 或运行时语法扩展。
- 自定义运算符、运算符重载、继承或原生对象模型。
- 把任意 Rust 对象、引用或方法直接暴露为 VM 值。
- 隐式 I/O、系统时钟、系统随机源、JIT 或原生代码生成。
- 为扩大类型数量而牺牲跨平台确定性。

若未来需求与这些边界冲突，应先修改架构目标和信任模型，而不是以局部便利绕过宿主效果协议。
